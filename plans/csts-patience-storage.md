# Prospective patience and storage changes

The completed Tranche 1 comparison retains its fixed 24-epoch schedule and published evidence. This revision prepares future runs and leaves experiment execution paused for review.

## Stopping rule

The [training configuration](../configs/csts-tranche-1.json) declares `patience=5` and `min_delta=0.0`. Check validation Spearman once after each epoch. A strict improvement over the best observed score resets the counter; a tie or regression increments it. Stop after five successive checks without improvement, completing at least the eight-epoch prefix window. Keep the checkpoint with highest validation Spearman and the earlier epoch for ties. Save terminal weights and optimizer state separately. The existing 24-epoch ceiling and resource ceiling remain in force. Reaching either ceiling supplies a budget limit; it provides no mathematical convergence certificate. `patience=null` retains the historical fixed-budget behavior.

The [patience tracker](../csts_pilot/early_stopping.py) implements this rule; the [training loop](../csts_pilot/convergence.py) records its counter, final reason, actual updates and learning rates. A positive `min_delta`, if explicitly chosen in a later design, measures the cumulative improvement since the last counter reset in Spearman units. Five epochs is a project choice. Patience-based stopping is a standard implementation pattern: see [PyTorch-Ignite EarlyStopping](https://docs.pytorch.org/ignite/generated/ignite.handlers.EarlyStopping.html).

Each loss arm can stop at a different epoch. The [selection verifier](../csts_pilot/convergence_run.py) requires identical initialization, initial RNG, schedule horizon, shared settings and pair order through their common epochs. It independently replays each stopping counter and records actual updates with `comparison_regime=validation_early_stopping`. This is a comparison under the same validation stopping policy. A claim about equal realized update budgets requires the fixed-budget mode. The scheduler horizon stays fixed when an arm stops early; its schedule is never compressed after seeing the curve.

A stationary point of a differentiable training objective satisfies $\nabla_\theta L(\theta)=0$. A small gradient is an approximate first-order diagnostic. For a twice continuously differentiable objective, a positive-definite Hessian at a stationary point is sufficient for a strict local minimum; a positive-semidefinite Hessian alone can be inconclusive. See Goodfellow, Bengio and Courville, [Deep Learning, chapter 4, sections 4.3–4.3.1](https://www.deeplearningbook.org/contents/numerical.html). Patience establishes a validation plateau under the declared observation rule. The saved batch-average losses and decaying learning rate leave stationarity unresolved. Any direct gradient diagnostic would require frozen weights, a fixed training objective and controlled stochasticity; it is outside this change.

## Native storage path

VIPER core remains unchanged. The pinned VIPER revision `e4ce91fa0a9330e769644aba0fccdfe062d5d821` already exposes `LocalStorageDestination`, sealed local run references and `execution.promote_run_to_cloud`. The change selects `destination="local"` in the [workspace settings](../viper.toml). `execution.run` continues to perform its native local verification. Downstream stages consume its immutable local references, and compute can proceed while network publication runs separately.

After each successful local invocation, the [runner](../csts_pilot/convergence_run.py) writes a durable publication request through the [background storage module](../csts_pilot/background_storage.py). The request captures the immutable source reference and the existing cloud destination. An independent CPU process holds a worker lock, performs native promotion and its native verification, and publishes a success receipt only after promotion returns. A single atomic JSON record is authoritative for each job. Re-enqueueing the same source and destination reuses the job. A crashed uploader resumes from that request; upload failures never invoke training. Three attempts are allowed automatically; exhausted failures remain visible for explicit publication-only retry:

```bash
python -m csts_pilot.background_storage --root /absolute/path/to/workspace --retry-failed
```

Publication status lives in `.viper/publication_queue/*.json`, with worker diagnostics in `.viper/publication_queue/worker.log`. The computational summary and queue status remain separate. An uploader spawn failure preserves its request and allows computation to proceed. An unwritable request is a persistence failure and halts the caller. Parent-process exit leaves the independent worker running; host shutdown stops that worker. Keeping the local store and queue intact permits a later retry. GPU shutdown during pending publication requires durable artifact staging and an independently running uploader; this revision supplies no cross-host transfer mechanism. Final closeout must require published receipts before removing its source storage.

The new runner records local invocation time and the queue records cloud-promotion time, including its native verification. Those remain combined timing categories.

## Review evidence

Focused tests cover strict improvements, ties, patience reset, required prefix completion, unequal valid stopping epochs, best versus terminal checkpoints, queue identity reuse, spawn failure, cloud retry, interrupted uploader recovery and enqueue progress during a blocked cloud call. These checks use synthetic CPU fixtures and controlled cloud collaborators. They establish control flow and persistence behavior; they supply no live-cloud latency benchmark.
