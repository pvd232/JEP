## Source and capture boundary

The existing full inventory has 17,334 canonical passage-condition identities: 13,744 training and 3,590 validation. It retains all 6,980 training and 1,830 validation comparisons and their original source groups. `source_inventory` uses the existing `answer_id`, chooses the first raw representative in original training-then-validation row order, and records all raw variants. Evidence quotations are checked against that representative; the semantic answer is reused over its canonical aliases. This preserves compatibility with the ongoing bank rather than changing its identities.

Generation receives only `id`, `passage` and `condition`. Source groups remain external and batch construction permits at most one item per source group. The full-capture controller checks the frozen source inventory hashes before generation, keeps the partitions separate and retains raw attempts. Missing and ambiguous records keep their original passage and original condition. Structural rejection stops or retries the preserved request under the unchanged policy; it does not create a shared missing-value embedding. The independent sample diagnostic also retains its explicit source-only rejection/fallback policy.

`proposition_provenance` pins the exact quality-gate bytes and all 24 supporting audit files and recomputes fresh judgment ID coverage, 58/60 faithful decisions and zero severe unsupported assertions. It binds the original audited capture source, validation source, prompt, schema, alias and effort. This is model-assisted development inspection, not expert verification or a guarantee that every generated answer is faithful.

Operational lock repairs have their own source identity. The original immutable `launch.json` retains the audited generation source; the controller records its executing capture/verifier identities separately. The standalone controller fetches the verifier and its full audit dependency closure from its pinned target commit. It does not rely on repository imports under `python -I`.

On completion, `propositions_tranche8_provenance.json` carries the source-only inventory and every successful raw prompt, input, schema, response, event log, checked record and receipt, together with the frozen audit evidence. Failed attempts remain in the source archive. Native import transports this fourth bank file with the answers, aggregate manifest and audit gate. Native preparation replays all successful raw capture checks after relocation, preserves original command paths as provenance, rejects tool activity and checks that the recomputed bank exactly equals the canonical bank used for transformation. A hand-edited `passed=true` receipt or source quotation alone cannot substitute for this chain.

## Native fitting and comparison

`proposition_run` retains the established native stages. Preparation publishes the exact transformed training/validation files. Epoch zero evaluates the selected saved Qwen adapter against those validation inputs without optimizer updates. The fitting stage restores adapter weights only from SHA-256 `8805f9a7241e4e19ffc481341ebad6f1ddb6dd6ff04bbf710f9f0896469e34ff`, starts fresh seed-7 optimizer/RNG state at epoch zero and reuses `TokenPairs` and `fit_neural`. The original prompt, final-token pooling, cosine-MSE, rank 32/alpha 32/dropout 0.05 attention adapters, batch 32/microbatch 2, constant 0.00002 rate, weight decay 0.01, patience five, 12-epoch ceiling and 14,400-second allowance remain unchanged.

Training answers supply optimizer inputs. Validation answers supply diagnostics and checkpoint selection. The native model, terminal model, optimizer/RNG resume state, transformed input hashes, trace, warm-start receipt and selected predictions remain standard artifacts. Saved inference checkpoints contain ordinary `FitConfig`, and the completed trace comparison now uses its JSON representation so tuple/list serialization does not falsely reject a successful phase.

The saved original-passage Qwen predictions remain the unchanged comparator; no baseline model is rerun and no new native control head is fitted. Predictions are restored to their original row metadata. Eligibility applies the existing Spearman gain of at least 0.005 and at most one-percentage-point deterioration in false-positive rate and condition ordering. Epoch-zero and adapted candidates are reported separately. Achieved-recall cutoffs retain the established integer-boundary tolerance and are frozen before any later test protocol.

Source/config must be clean and committed before direct native execution. The shared original-workspace GPU lock serializes the existing owner. Operational deployment, formatting and supervised execution additionally share a workspace lease so a checkout cannot change under a live child. The worker separately binds dispatcher code and its explicit target source; formatting export remains a named phase with a distinct reviewed target. Capture partition/batch locks are inherited by CLI children, and interrupted recovery requires an explicit request after those owners release the locks.
